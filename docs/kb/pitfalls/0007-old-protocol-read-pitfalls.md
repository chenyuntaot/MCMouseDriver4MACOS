# 踩坑记录：旧协议读路径的三个真机坑

2026-08-08 在 A7 V2 Pro+（2.4G 接收器 1K 模式，macOS hidapi）上首次跑通读路径时
发现，均已在代码与相关条目中修正/登记。

## 1. 响应缓冲区在"编码版/明文版"之间交替

对同一命令连续 `get_feature_report`，设备缓冲区在两种形态间交替：

- 编码版（官方协议形态）：`F9 C8 C7 E7 BF …`（XOR 解码后 = `06 37 38 18 40 …`）
- 明文版：`06 37 38 18 40 …`（未取反，子命令与数据直接可见）

表现为偶数次读到编码版、奇数次读到明文版。**对策**：按子命令回显校验
（kb/0003 §2），不匹配就重读——官方代码的"指令混发了"重试（76598-76604）
很可能就是在处理同一现象。`OldProtocolSession.query` 已实现该重试。

## 2. 设备信息字节的 bit 顺序与官方 parser 字面相反

`0x11 0x06` 的 byte8，官方 binary-parser 声明为 `bit3 connectMode | bit1
connectStatus | bit4 保留`（76282-76284）。binary-parser 的 bit 字段从 MSB 读，
按此应为"高 3 位=connectMode"。**真机数据证伪**：实测 byte8=0x09，
MSB 读法得 mode=0（有线）status=0，与实际（2.4G 已连接）矛盾；
**LSB 读法 bit0-2=mode=1（2.4G）、bit3=status=1（已连接）完全吻合**。
已在 `parse_device_info` 与 kb/0005 §1 修正。

教训：binary-parser 的 bit 声明不能直译，bit 级字段一律以真机数据校准。

## 3. 鼠标睡眠时接收器返回全零配置

鼠标休眠时，通过接收器读 `0x12 0x67`（整份配置）回显匹配但**数据全零**；
`0x11 0x06` 返回的是接收器缓存的鼠标信息（vid/pid/电量 59% 均正确）。
鼠标唤醒（移动/点击）后 `0x67` 返回真实配置。

对策：读到 dpi_count=0 或全零配置时提示用户晃动鼠标后重试；
GUI 期可考虑读前先发无害命令唤醒。

## 4. 已解决：按键区的 nibble 顺序（2026-08-09 仲裁）

官方 parser（`Awt` 76288+）声明读布局按键字节 = 高4位 buttonType | 低4位
buttonIndex，写布局（`0x12 0x57`）相反（kb/0006 §1.5）。真机默认配置读回
`00 10 20 30 40 50`（各键 value=0）：按官方读法是"键n type=n"，语义不通；
按**写布局**（高4位=index）解读为"键n 均为恢复默认（type=0）"，语义合理。
疑似官方读 parser 声明与固件实际布局不一致，或默认值恰为歧义数据。

**仲裁实验（2026-08-09）**：写 `0x12 0x52`（index=4, type=5, value=0x010000）
后读回，按键字节 = `0x45`（高4=index、低4=type）。**结论：读写布局一致，
均为高4位=buttonIndex、低4位=buttonType**；官方读 parser 声明有误。
`parse_config` 已按真机结论修正。

## 5. 全零配置写回风险（已加防呆）

抓写样本时曾在鼠标休眠状态下读到全零配置并**误发全零 DPI 写命令**
（所幸休眠中的设备未应用，配置无损）。教训：

- `OldProtocolSession.write_dpi` 已加防呆：dpi_count=0 或全零 DPI 表直接抛错。
- 任何"读-改-写"流程必须先校验读回数据非零。
- 抓样本脚本同样必须先断言数据有效再发写命令。

## 6. 已解决：byte1/2 的字节序与 nibble 序（2026-08-09 仲裁）

现象：写回报率（`0x11 0x41`）后按官方 parser 声明的位置（byte1 低4位
gRateIndex）读回校验，永远不变，误判"短包写不生效"；写休眠/防抖也一度误判。

**仲裁实验（2026-08-09，全字节 diff）**：

| 写入 | byte2 变化 |
|---|---|
| `{usbRate:0, freeRate:1}` | 0x22 → 0x12 |
| `{usbRate:1, freeRate:0}` | 0x22 → 0x02（无线连接下 usbRate 被忽略，仅低位不变） |
| `{usbRate:2, freeRate:2}` | 恢复 0x22 |

**结论**：byte2 = [freeRate(高4) | usbRate(低4)]，即读布局 byte1 =
[usbRateIndex|usbDpiIndex]、byte2 = [gRateIndex|gDpiIndex]——与官方读 parser
声明（byte1=g、byte2=usb、且 nibble 相反）**完全相反**，但与 0x57 写 schema
（`mMt`）的字段序一致。此前 byte1 两 nibble 恰好都是 2（1000Hz + 第3档），
造成"官方声明看起来对"的假象。

同批验证：休眠 `0x0A`（byte19）、防抖 `0x43`（byte18）、传感器 `0x42`
（byte17 bit2）写均生效——**0x11 短包写本来就有效**，问题全在读回校验位置。

教训：本固件的 binary-parser 声明在 bit/nibble/字节序上已三处与真机相反
（设备信息 bit、按键 nibble、rate/dpi 字节）。凡 bit 级布局一律以真机 diff 仲裁。

## 7. 宏排查实录（2026-08-09，固件 5.42.0.9，有线与 1K 接收器均试）

目标：宏写入槽位并物理触发。逐层排障结论：

1. **`0x12 0x65` 读宏在本固件可用**（官方 bundle 中的死代码）：
   `12 65 <slot> <part>`，响应 = [buttonIndex, moreData, offset, length,
   trigger, condition, time, count, 事件×52]。是调试宏的利器。
2. **事件必须发逻辑原形**：官方 bundle 的事件是"预取反"的，本固件收到
   取反事件会全部丢弃（0x65 读回 length=6、事件全零，但 count 保留）。
   逻辑原形（[00,81,04,00] 等）则正常存储（length=18=12事件字节+6）。
   **包头仍然要取反**——本固件是"头取反、事件不取反"的混合形态，
   与 bundle 代码不符，疑似固件版本差异（官方最新参照 5.48.1.4）。
3. **`0x12 0x52` 绑定写会清空对应槽位的事件**（0x53 写名不会）。
   正确顺序：**先绑定（type=4）→ 再写数据（0x55）→ 写名（0x53）**，
   绑定之后绝不能再发 0x52，否则前功尽弃。
4. 绑定 type=4 可粘住（value=0 或槽号均试过）；slot 无有效事件时用 0x57
   写 type=4 会被固件打回 type=0（侧面证明固件会校验槽位有效性）。
5. **已结案（2026-08-09）**：事件在槽、绑定粘住、名字在槽，但旧固件
   5.42.0.9 物理不触发。**固件升级到 5.42.2.4 后宏正常触发**——
   旧固件宏引擎本身失效，且事件编码也随固件变化：新固件恢复官方 bundle
   的"预取反"形态。另注：官方 Web UI 对本机型不开放宏编辑（截图存证），
   但固件实际支持，官方 App 能正确显示本工具写入的宏名与绑定。
   `OldProtocolSession.write_macro` 已实现"写后读回（0x65）自动探测编码
   并重试"，对两种固件形态自适应。
6. 排障副产品：`0x12 0x65` 读宏在本机固件可用（官方死代码），响应 =
   [buttonIndex, moreData, offset, length, trigger, condition, time, count,
   事件×52]，length = 事件字节数 + 6，是调试宏的利器。
